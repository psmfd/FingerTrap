01 / Decision & scope

Approve S3 as six reviewable checkpoints.

I recommend implementing the isolated launch foundation now, using the existing Pi executable architecture. S1 established profile identity and compatibility; S2 established reproducible imports. S3 makes those profiles meaningful at the process boundary, preparing the storage and extension work in S4 and S5.

Expected result: two concurrent managed test profiles can launch through RPC and PTY without borrowing the operator’s environment or each other’s state. Invalid runtime selection fails before execution. Existing user-managed Pi and ordinary shell panes retain their behavior.

Approval covers implementation and verification of this foundation. The normal application will continue rejecting managed activation until storage, discovery and runtime qualification gates are satisfied.

S3 delivers

Explicit, verified launch inputs

Host-owned context; executable/resource validation; replacement environments; native compatibility; shared service integration; process and regression evidence.

Subsequent work

Complete product activation

Profile-aware browsing/resume/meters in S4; imported dispatchers and tools in S5; full assembled-runtime qualification in S6 and #202; installation/login through #187/#203.

The overall #200/#201 implementation plan remains approved. This document supplies the focused S3 review you requested. It does not reopen the earlier ownership or executable-versus-SDK decision.

03 / Proposed design

Resolve once, then pass immutable launch inputs.

  1. 1. Trusted selectionHost selects profile, runtime descriptor and permitted resources.
  2. 2. ValidationCheck identities, real paths, files, digests and launch policy.
  3. 3. Launch contextFreeze argv, cwd, environment and non-secret profile identity.
  4. 4. TransportRPC or PTY consumes that same context and supervises the child.

One resolver for Pi panes

Introduce an internal PiLaunchContextResolver and immutable PiLaunchContext. Both pane services use them. User-managed resolution delegates to the existing executable precedence; managed resolution accepts only host-selected profile/runtime inputs. Transport-specific arguments, such as --mode rpc, are composed centrally and passed as individual arguments.

The managed context contains the profile/runtime IDs, absolute executable, verified resource selection, explicit working directory, environment mode and copied environment map. It contains no raw credentials. No per-launch code changes the sidecar’s process-wide environment or current directory.

Runtime descriptor and filesystem checks

Define a versioned host-owned runtime descriptor: runtime ID, fork revision, target OS/architecture, relative executable path and digest, resource entry points, and a bounded inventory of required files and dependency digests. Its expected identity comes from trusted host configuration, not a manifest supplied beside an arbitrary WebView path. Keep immutable runtime files separate from writable profile state.

Check descriptor/profile agreement, executable permissions, required dependencies and canonical containment before spawning. Reject missing files, mismatched hashes, traversal, duplicate/case-alias paths, and symlinks or Windows reparse points that escape the selected roots. Create profile directories only beneath the supplied application-data root, with appropriately restrictive access. A string-prefix path check is insufficient.

The descriptor is a launch-verification contract, not an installer. S3 fixtures supply reviewed temporary artifacts; #187 supplies production installation and activation later. Define size/count limits and actionable error categories with the contract. Diagnostics identify the failed check without dumping the child environment.

Request boundaries

The WebView can request a pane and working directory; it cannot select a managed executable, rewrite profile roots, inject reserved environment variables, disable verification or grant trust. Validate and canonicalize the working directory independently of profile storage. Reject raw managed environment/executable overrides. Until S4 implements profile-aware resume, reject managed SessionPath requests rather than resolving arbitrary historical paths.

Tests inject a verified host fixture into the same resolver and pane services. No environment variable, settings switch or public RPC parameter will bypass the production activation gate. Add an ADR extending ADR-0035 for these launch and native-environment semantics.

04 / Isolation policy

A replacement environment starts empty.

Proposed managed launch policy
InputHow S3 supplies it
Pi stateSet PI_CODING_AGENT_DIR and PI_CODING_AGENT_SESSION_DIR to the S1 profile paths; use an explicit session-directory argument where supported and verified.
Home and cachesSet HOME/USERPROFILE and platform app-data/XDG locations beneath the selected profile. Set TMPDIR/TMP/TEMP to its temporary directory. Cover supported platform aliases so a library cannot silently return to the operator’s home.
Executable and PATHLaunch the verified absolute binary. Construct PATH from reviewed runtime/tool locations and necessary platform directories; reject relative or empty segments. Do not copy the startup login-shell PATH.
Terminal / platformSupply TERM for PTY explicitly; carry only documented locale and essential OS variables. Windows system directories come from validated host/platform values. Test the allowlist on each platform.
Credentials and hooksExclude ambient provider keys, cloud profiles, agent sockets, credential-helper overrides, proxy configuration, NODE_OPTIONS/NODE_PATH and dynamic-loader hooks. S3 uses synthetic credentials or no credentials; unresolved credential references fail.
Profile contextPropagate only non-secret IDs and profile paths to controlled children. Real credential retrieval remains a trusted-host responsibility; no secrets in argv, descriptors, fixtures or logs.

Validate names, NUL characters, duplicate keys and platform case rules before spawning. In replacement mode, an empty map means an empty environment and an empty string is a literal empty value. The inherited mode retains each existing API’s compatibility behavior, including PTY’s historical empty-value removal.

Discovery must be proved separately

The pinned fork exposes explicit agent/session directories and resource-disabling flags. However, its resource loader resolves packages before final extension selection, and startup settings are read before the final runtime trust decision. Auth storage also supports configuration-value resolution. These observations make a complete startup audit necessary; the flags alone do not certify isolation.

Audit settings, models, auth, packages, extensions, skills, prompts, themes, AGENTS/CLAUDE context, SYSTEM/APPEND_SYSTEM prompts, trust state and credential helpers. Establish a fixed managed argv/resource policy using only verified controls. Exercise both initial launch and reload paths. Start with no optional resources, then one harmless explicitly selected fixture extension; do not auto-load the imported meters yet.

First decision gate: if the exact executable cannot suppress an ambient source or enforce the required resource policy, record the gap under #201/#202 and keep that managed scenario disabled. Continue independently verifiable launch plumbing, but do not label the blocked discovery acceptance complete. A fork change, pin bump or SDK switch needs its own review.

This is configuration and process-launch isolation. It does not prevent a deliberately malicious process from reading files accessible to the OS user. Likewise, an environment cannot stop Git or a shell from intentionally loading repository/system configuration: the controlled child probe belongs here, while migrated tool/dispatcher policies and their real helper chains remain S5 work.

05 / Execution order

Six checkpoints, each with a clear exit.

S3-A · Contracts and pinned-runtime audit

Define the launch boundary before enabling a path.

Add the launch ADR, immutable context, descriptor contract and discovery matrix. Map every relevant Pi source to its control and required probe. Specify failure categories and bounds; retain the production gate. Reuse S1 profile definitions rather than adding another profile schema.

Exit: contracts reject invalid identities and requests; every discovery category has evidence or an explicit blocker. No unresolved control is treated as supported.
S3-B · Context and artifact resolution

Construct the complete managed launch input.

Implement verified artifact selection, filesystem checks, profile-directory preparation, explicit cwd, replacement environment and resource arguments. Use immutable snapshots so concurrent launches cannot share a mutable dictionary. Keep credentials unresolved outside the trusted host seam; use empty or synthetic selections in tests.

Exit: two profiles produce independent contexts; missing or modified artifacts and escaped paths prevent process creation; a permissive request cannot weaken managed policy.
S3-C · RPC transport

Make replacement an explicit client option.

Add Inherit/Replace semantics to PiRpcClientOptions, defaulting to inherited behavior. Clear ProcessStartInfo.Environment for replacement, then apply the validated snapshot. Extend FakePi to report selected synthetic variables, cwd and a controlled child’s observations.

Preserve hello/request deadlines, bounded JSONL/stderr/event buffers, backpressure and EOF → TERM → KILL cleanup. Verify cancellation during startup and normal shutdown through the real process boundary.

Exit: inherited-mode regression tests remain green; replacement RPC children lack synthetic parent-only values and retain exactly the permitted test values.
S3-D · PTY and native ABI

Carry replacement all the way to the OS.

Add the same explicit mode to PtyOptions. In replacement mode bypass parent/platform merging, copy inputs, and never mutate the caller’s options. Preserve the current inherited path for shell panes and existing callers.

On macOS/Linux, introduce a distinct native export for replacement execution, leaving the existing export compatible. Pass a non-null terminated environment array even when empty; use absolute-path execve with the supplied environment. Construct TERM and other defaults before the native call, avoiding replacement-mode child-side environment mutation.

Update both P/Invoke wrappers. A missing new export or stale native companion produces an actionable error; never retry through inherited execution. Preserve Darwin’s spawn gate and FD_CLOEXEC handling, including failure cleanup. Verify exec failure, descriptor ownership and cancellation/reaping behavior with real native launches.

On Windows, provide a correctly terminated explicit Unicode block, handle key casing and literal empty values, and bypass ambient PATH lookup for replacement. Update the vendor patch table and verify the new native library reaches the published sidecar and Apple Silicon package.

Exit: real PTY probes prove replacement on supported test platforms; old-companion failure is safe; inherited shell behavior and spawn coordination remain covered.
S3-E · Shared pane-service integration

Use the same policy in RPC and Pi PTY panes.

Wire the resolver into RpcPaneService and Pi launches in PtyService. Compose production dependencies in Program.cs with managed activation still unavailable. Keep ordinary shell-pane launch logic intact. Verify managed request rejection and service cleanup using an internal host fixture, without exposing a public activation bypass.

Exit: both services launch the verified fixture with the same profile policy; production settings still fail closed; user-managed and shell compatibility tests pass.
S3-F · Integration evidence and handoff

Prove behavior under contamination and concurrency.

Run the acceptance matrix below. Use a harness with synthetic operator files and secrets, never the developer’s real credentials. Exercise the exact pinned Pi artifact where available and record its digest; keep fake-process results distinct from pinned-runtime results. Retain a reproducible probe command and fixtures in the repository.

Run the affected package, sidecar, native, structural and hosted checks. Record representative deliberate regressions that make the new guards fail, restore the code, then run the final checks. Publish checkpoint evidence to the existing draft PR and durable records.

Exit: all applicable S3 acceptance cases have evidence; unresolved platform/runtime gaps remain named and block the corresponding completion claim. The next slice is S4, with managed activation still gated.

Local and hosted validation

Use audited locked .NET restore, a Release build, the sidecar suite, real native probes and scripts/smoke-pty.py. Run runtime-package provenance/lint/typecheck/tests when that package changes. Run repository/whitespace checks for every checkpoint. Preserve RPC goldens and bound checks.

Collect Linux, Windows and macOS CI results for the source commit being reviewed. macOS ARM64 receives local native and packaged-companion evidence. A platform job that skips a required native scenario is recorded as a coverage gap, not a pass for that scenario. Full product/Finder/login acceptance stays with the later release gates.

Demonstrate at least the inherited-environment regression, native replacement regression, resource-verification omission and managed-gate bypass fail their intended tests. Keep only meaningful behavioral tests, and restore each temporary mutation before committing.

S3 is complete only when its applicable acceptance evidence is recorded. FakePi proves host plumbing; real PTY probes prove native semantics; the pinned executable proves discovery behavior. None substitutes for the others. S3 alone does not close #200 or #201.

08 / Continuity and limits

Every checkpoint leaves a precise resume point.

Before S3-A through S3-F, update STATUS.md with the active checkpoint, intended change and validation. Append meaningful results and failures to WORK_LOG.md as they occur. Record source hash, commands, test counts/skips, remote backup, CI identity and remaining blockers separately.

Use scoped commits on the current migration branch and back them up to the existing draft PR #207. The final report belongs in the repository, with only supplementary raw logs in temporary storage. A handoff identifies the next command or file to change; it never relies on chat memory.

Rollback and deployment boundary

The inherited mode remains the default for existing callers and the managed production gate remains closed. Source rollback is a scoped revert of the affected checkpoint. Build/package rollback must keep the sidecar and native companion together; an older native companion must cause an explicit replacement-mode error.

No operator state is migrated, no global runtime is installed and no live profile is activated by S3. S4 handles stores, browsing, resume, recovery metadata and meters. S5 handles actual imported subagents/tools and their credential/configuration policies. S6/#202 handles the assembled runtime; #187/#203 handles production installation, credential authority and activation. SDK evaluation and pi_config retirement retain their existing separate gates.

Principal uncertainty: whether every required discovery control exists in this exact fork. Resolve it early and preserve the evidence. Environment replacement and artifact validation can advance independently; a known discovery gap must remain visible in the work board.
