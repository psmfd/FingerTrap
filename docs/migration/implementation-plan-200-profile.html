01 / Recommendation & scope

Build the profile foundation, then migrate in bounded slices.

Approved on 20 October 2026. The maintainer approved this plan and requested durable tracking across failures and sessions. Follow the current status and resume instructions and activity log for implementation progress.

Recorded scope: #201 + #200. The original request named #210; that lookup returned “Not Found,” and this plan disclosed the proposed #201 mapping before approval. No requirements are attributed to #210.

Recommended next implementation: define the shared profile contract, prove it with the already imported token and cache meters, and extend the import tooling before moving the remaining components. Profile work and source review can overlap; activation follows successful isolation and runtime qualification.

FingerTrap becomes the place where retained runtime source and fixes evolve. pi_config supplies immutable source snapshots and historical evidence during the transition. Each migrated component gets one owner, a recorded source identity, and its applicable regression tests.

  1. 1. EstablishProfile schema, compatibility mode, explicit resource selection.
  2. 2. ProvePTY, RPC, storage and resume agree for two isolated profiles.
  3. 3. ExpandImport complete dependency and test sets; carry pending fixes.
  4. 4. QualifyReal pinned executable, child propagation and failure recovery.

Backend decision: retain the current Pi executable/RPC integration and v0.85.1-psmfd.1 baseline. The profile contract will also serve a future SDK worker, but a backend switch belongs to #202 and a successor ADR. If the current fork cannot enforce a required discovery boundary, record that gap and block managed activation until an explicit fork change or backend decision is qualified.

03 / Managed profile contract

One resolved context for the entire process tree.

Add a sidecar-owned RuntimeProfile and immutable ResolvedLaunchContext: profile ID and schema version, runtime identity, resource manifest, canonical storage roots, workspace cwd, launch environment, credential references, and supported capability gates. A versioned, non-secret projection gives TypeScript consumers the same context. Shared fixtures verify that the two implementations agree.

Proposed storage and resource ownership
AreaProposed contract
Profile root<FingerTrap app-data>/profiles/<id>/, using the existing platform path convention. Validate IDs and canonical paths; missing or invalid managed roots are errors, never a fallback to the cwd or operator home.
Pi stateAn explicit profile-local agent directory for settings, models and sessions. Preserve supported Pi file formats. Keep application profile metadata separate from Pi settings.
CredentialsPersist references in profile metadata. Resolve only explicitly configured credentials through the established trusted host boundary. No automatic import of provider variables, operator auth files, GitHub tokens or credential-helper settings. Production login/brokering remains a dependency where incomplete.
Extension stateProfile-local roots for meters, shared state, worktree manifests, caches and temporary files. Preserve recorder schemas while replacing hidden home-directory defaults.
Runtime resourcesA versioned immutable resource manifest identifies the exact executable, package dependencies and selected extension/default files. Source ownership and enabled-resource lists remain separate.
WorktreesKeep Git worktrees in the repository’s supported .worktrees layout. Qualify names and manifests by profile/session to avoid collisions. Recovery must respect recorded host and process ownership.
Repository identityStore per-repository identity overrides outside tracked source, scoped to profile and canonical repository identity. Define explicit opt-in compatibility for existing untracked identity files from pi-gh-identity-guard #10; never copy live values into the package.

Launch and discovery rules

  • Managed mode is explicit. Existing installations retain user-managed behavior until opted in. A managed failure never falls back to an ambient executable, profile or auth source.
  • Resolve once, propagate everywhere. PTY and RPC Pi sessions, resume, subagents and auxiliary tool children receive the selected executable, profile and explicit cwd. Child credentials are narrowed to the operation’s needs.
  • Construct the child environment from an allowlist. Supply profile-local HOME/USERPROFILE, XDG and temporary roots plus required OS/terminal variables and approved tool paths. Exclude ambient provider keys, preload variables and credential-helper configuration. Do not mutate the sidecar’s process-wide environment during a launch.
  • Verify the exact fork’s discovery controls. Enumerate global, user, package and project resource loaders, including extensions, agents, rules, skills and prompts. Managed mode loads only selected resources; project additions require an explicit supported trust path. Assert each extension initializes once.
  • Treat WebView inputs as requests. Resolve profile IDs and session references in the sidecar; reject caller overrides of managed roots, executable, resource lists or credentials. Resume must stay within the selected profile, including symlink and traversal checks.

Boundary of the guarantee: this establishes independent configuration, discovery and state for managed launches. It does not make arbitrary same-user code an operating-system sandbox. Native approval and confinement guarantees still require their own designs and tests.

Preserve ordinary shell-pane behavior. Audit the startup login-shell PATH enrichment separately: managed selection must use its explicit tool paths, and credential helpers or login scripts must not reintroduce ambient state through a child command.

04 / Implementation sequence

Six reviewable changes, each with exit evidence.

Use separate commits or PRs for these boundaries. The first implementation milestone is steps 1–4: a working isolation foundation with the two meters. Steps 5–6 expand and qualify the retained runtime. A foundation-only delivery leaves the wider issues open.

Step 1 · Baseline and contract · #201 + #200

Record the profile schema and approved source slices.

Reconcile the existing M0/M1a changes into reviewable history, preserving unrelated local artifacts. Refresh source and pending-fix identities. Document profile schema, mode precedence, resource selection, path ownership, credential references and compatibility behavior.

Touchpoints: docs/migration/; sidecar settings models and validation; a versioned contract under packages/agent-runtime/. Add explicit profile selection to pane/session requests only where needed.

Exit: approved contract fixtures cover two profiles, invalid settings and missing managed runtime; existing user-managed settings remain valid.
Step 2 · Reproducible imports · #200

Make the package support reviewed incremental imports.

Replace the single 20-file assumption with an explicit per-slice manifest and aggregate verifier. Record source repository, commit/blob, destination digest, notices and transformations, including fixes derived from separate PR heads. Reject missing, duplicate, escaped and unaccounted imported paths.

Register each slice’s inherited test suites explicitly. Retain isolated temporary homes, clean environments, locked dependencies and disabled install scripts. Each slice must restore and validate without a private checkout or home-cache symlink.

Exit: the original 20 files and six suites remain accounted for; deliberate hash/path/suite omissions fail; the independent package passes its checks.
Step 3 · Launch isolation · #201

Apply the context to RPC and native PTY launches.

Introduce one resolver shared by PiExecutableResolver, RpcPaneService and PtyService. Add explicit inherited-versus-replacement environment handling to the RPC client and vendored PTY interface. Carry replacement semantics through the Unix native spawn and Windows environment block; preserve vendor provenance.

Keep per-launch cwd and environment independent under concurrency. Extend FakePi and real PTY probes to report selected context using synthetic values. Preserve startup deadlines, bounded output, backpressure, cancellation and process-tree cleanup.

Exit: concurrent PTY/RPC children see only their own profile and approved variables; absent or mismatched managed resources fail clearly; existing user-managed launches still pass.
Step 4 · First complete profile slice · #201

Connect storage, session browsing and the two meters.

Inject profile roots into SessionStore and WorktreeReconciler, then expose profile identity through session-list and resume requests. Preserve ADR-0028’s bounded metadata scan, TotalCount, corrupt-file reporting and absence of extension-starting inspector processes.

Add a common runtime path/context helper and update every token/cache-meter entry point, settings reader and writer to use it. Add compatibility fixtures for existing JSONL records. Track profile identity in crash/recovery state and review shared registry concurrency so one profile cannot reap a live sibling’s child.

Exit: two profiles can record, list, restart and resume independently; synthetic operator files stay untouched; cross-profile resume is rejected. The controlled test fixture may load meters, while normal app discovery stays gated.
Step 5 · Remaining source and fixes · #200 + #201

Import each component with its complete dependency and test set.

Use the waves below. For every retained component, enumerate shared modules, vendor files, fixtures, runtime dependencies and activation gates before exporting exact Git blobs. Adapt paths and child launching to the established profile contract; record behavior changes separately from relocation.

Reapply the subagent declaration/shadowing and patch-audit fixes from pi_config PR #1170 independently of its version bump. Reconcile #280’s legacy spawn-error patch against current serial execution. Preserve errors, aborts and cleanup; retain protected project-agent restrictions.

Exit: every retained component has provenance, independent tests, a source owner and a stated activation disposition. No dispatch becomes available before its restriction and child-isolation tests pass.
Step 6 · Integration and completion · #201 + #200

Qualify the assembled profile using the pinned executable.

Run the approved resource set through real PTY and RPC launches on macOS ARM64, including a subagent and tool subprocess. Use synthetic credentials or an isolated local provider fixture for deterministic tests. Record exact runtime hashes, loaded resources, path observations and failure results.

Run the relevant package, sidecar, UI and native checks; obtain hosted CI evidence. Update the migration ledger and issue checklists with precise completed scope. Managed installation and general activation remain coordinated with #187 and #202.

Exit: the acceptance matrix below passes for the retained scope; unresolved components remain explicitly disabled and tracked; issue closure matches actual evidence.

07 / Dependencies & rollback

Keep the migration separable from backend and release decisions.

DependencyHow this plan handles it
#202 · Fork / SDK qualificationConsumes the same profile contract. Required CLI discovery gaps become explicit blockers. A newer fork release or npm type package is not qualification evidence.
#186 / #187 / draft #188Coordinate onboarding, runtime artifact layout and supported login. This plan supplies a verified development fixture and profile interface; installer, updater and distribution acceptance stay there.
#203 · Trusted authorityNo new native approval bridge, protected package-agent dispatch, credential grants or FT-3 access. Existing TUI/refusal restrictions remain; RPC/SDK hosts must never claim TUI mode to bypass them.
#204 / #205Expertise platform readiness and pi-workflow integration remain separate. Preserve contracts and blockers without claiming macOS support from Linux-only evidence.
#206 · RetirementRecord component ownership here now. Archive pi_config or change mirror publishing only after replacement consumers and recovery paths are verified.

Rollback strategy: managed mode starts opt-in with a versioned profile and resource selection. Do not rewrite the operator’s existing Pi installation or automatically move live sessions/auth. A failed profile selection leaves the prior data intact and reports the failure. A deliberate switch back to user-managed mode launches a new session; it never changes the backend underneath a live session.

Highest implementation risks: native PTY environment inheritance, project resource discovery, credential-helper side effects, shared crash-registry concurrency and subprocesses that reconstruct legacy paths. Resolve these with process-level evidence early. If a dependency blocks activation, continue safe source ownership work and leave that capability disabled with a linked blocker.
