Runtime migration · S3-G · #201 / #202

Give managed Pi launches an explicit discovery policy.

Keep the executable and RPC architecture. Add a small, versioned startup policy to the Pi fork, then prove that FingerTrap can launch it in an existing project without consuming or migrating ambient configuration.

Proposed · approval pendingFive implementation checkpointsProduction activation stays gated
01 · Decision

Resolve discovery in the runtime that performs it.

Recommendation: implement an opt-in managed-v1 startup policy in psmfd/pi, selected by FingerTrap only for a verified candidate artifact. Apply that policy before configuration, command dispatch, migrations or resource discovery can have side effects. Carry it through reload and runtime recreation.

FingerTrap already owns launch selection, profile paths, executable verification and process environment replacement. The remaining gap is inside Pi. Fixing it there preserves the existing PTY and RPC paths and avoids expanding this slice into a second backend.

Expected result: a keyless managed fixture can start in a real repository containing existing .pi configuration, preserve that configuration, and load only its explicitly selected local resources.

FingerTrap remains the owner of migration work, imported extensions, qualification and future distribution. The Pi repository remains an upstream runtime dependency. No new implementation belongs in pi_config.

This is a proposal. No Pi patch, artifact capability, new runtime pin or managed product activation has been implemented in this planning step.

02 · Starting point

The process boundary works; the startup boundary is incomplete.

Merged and verified

S3 launch foundation

Shared PTY/RPC resolver, independently trusted artifact descriptor, complete file hashes, profile-derived paths, explicit cwd and native environment replacement. PR #207 merged as 9bfc092; protected dev CI and local Apple Silicon packaging passed.

Still blocked

Arbitrary project discovery

The exact pinned binary renames .pi/commands to .pi/prompts before the trust decision, despite discovery-disable flags, denied trust and offline mode. Current managed fixtures therefore reject project .pi state.

The baseline is v0.85.1-psmfd.1 at e7d09c9dc5fca409f46a5476669e3c0404054d69. The retained audit and executable probe demonstrate the rename. A successful probe exit currently means the known defect was reproduced.

  1. Early commands / setupAuth handling, install cleanup, bootstrap settings and proxy setup precede normal argument parsing.
  2. CLI parsingThe existing discovery and trust flags become ordinary parsed options.
  3. Migrations / stateLegacy migrations, startup settings and session selection run before runtime trust resolution.
  4. Trust / resourcesResource loading and package resolution have their own paths; reload can recreate those services.

Source inspection of the latest published fork, v0.87.1-psmfd.1 at 42429b94e4aca33fdbb8d094de29758b36411ba1, shows the same bootstrap/migration ordering. That candidate has not passed FingerTrap executable qualification; a version upgrade alone is not an established fix.

This plan covers startup and resource discovery. It does not establish an OS filesystem sandbox or restrict arbitrary filesystem access by trusted extensions and agent tools; those have separate ownership and enforcement work.

03 · Architecture choice

Retain executable/RPC for this slice.

Options considered
OptionAssessment
Add only --no-migrationsAddresses the reproduced rename, but leaves early settings, package resolution, prompt discovery and recreation paths to qualify. Too narrow as the S3 completion criterion.
Change cwd or hide project filesChanges project semantics or mutates the user's repository. Does not provide a durable runtime policy. Reject.
Upgrade to the latest forkIncreases the comparison surface and still requires a discovery fix and exact artifact qualification. Keep it a separately reviewed pin decision.
Move to the Pi SDK nowOffers explicit application control, but also introduces a JavaScript worker, packaging, protocol and lifecycle responsibilities. Default SDK resource services still need an explicit discovery policy. CLI-based PTY and child sessions remain relevant.
Explicit managed CLI policyRecommended. Reuses the current process architecture and addresses the runtime behavior at its source. The same policy can inform a later SDK comparison.

Continue the SDK evaluation under #202 after a qualified executable comparator exists. ADR-0034 requires evidence for a production SDK switch; this blocker does not by itself establish that case.

04 · Proposed behavior

One explicit policy, selected before side effects.

Proposed CLI syntax: --startup-policy managed-v1. This is a new API to implement, not an existing Pi flag. Use the existing host-resolved cwd, agent/session paths, literal system prompt and verified extension arguments; avoid introducing another configuration manifest solely for this mode.

Initial managed-v1 contract
BoundaryRequired behavior
Entry and parsingRecognize and validate the policy at the earliest entry point, before command handlers, cleanup, settings or migrations. Audit module initialization too. Reject unknown policy versions, duplicate selectors and conflicting options before startup work. Standalone CLI launches without the selector retain their established behavior.
Settings and migrationSkip all implicit project and profile migrations, first-run setup and install cleanup. Use explicit in-memory defaults/host inputs. Do not read implicit project or global settings, auth, models or keybinding files. Command-valued config must never execute. S3 uses synthetic, keyless inputs; credentials remain a later gate.
Resources and packagesBypass automatic package resolution and installation, extension/skill/template/theme discovery, ancestor/home instruction collection, and SYSTEM/APPEND_SYSTEM discovery. Accept only selected local extension paths inside the verified artifact and the explicit literal prompt. No registry/git package references, automatic helper downloads or discovered resource expansion.
Project semanticsPreserve the real repository cwd. Existing project configuration is ignored and left intact, including symlinked .pi state. Never silently trust the project, rename/hide its configuration or substitute an empty cwd.
LifecycleCarry an immutable typed policy into settings/services/resource loaders and runtime factories. Reload and same-profile new sessions retain it. Resource-extension APIs cannot re-enable discovery. Unsupported install/config/auth commands, resume/switch requests and cwd changes are rejected until explicitly supported; no fallback to default discovery.
State and processAllow only deliberate Pi session/runtime state beneath the selected profile roots. Retain FingerTrap's environment replacement and explicit PATH in both transports. A policy is not a process-wide mutable flag and must not change another pane's behavior.

Bind policy support to verified artifact identity

Extend FingerTrap's strict artifact descriptor to v2 with a required startup-policy capability. Preserve the independent descriptor digest, complete inventory, platform checks and bounded parsing. Tie the capability to an exact reviewed candidate revision and file hashes supplied by the host. A version string or a runtime's self-reported capability is insufficient.

The host must reject an old descriptor, unsupported policy or unselected revision before creating a managed process. Keep the original baseline as a negative comparator. Only the qualified candidate fixture gains permission to launch with project .pi present; profile configuration, raw overrides, credentials and resume restrictions stay in place until their own contracts are implemented.

Do not weaken the existing guard first. Removing the project-directory rejection depends on verified policy support and passing real-process tests. Production composition continues to provide no managed selection.

05 · Delivery order

Five independently reviewable checkpoints.

S3-G1 · Contract and failing evidence

Specify the boundary and preserve the failure.

  • Add the next sequential ADR extending ADR-0036 for managed startup policy and artifact capability. Record the exact policy surface and explicit exclusions.
  • Create a linked Pi regression issue under FingerTrap #201/#202. Prepare an isolated worktree from the pinned revision; preserve existing sibling checkouts and unrelated work.
  • Keep the current blocker-reproduction script. Add a separately named qualification suite whose success means isolation passed, with a known-bad baseline comparison.
  • Turn the audit into executable fixtures for early settings, migrations, package resolution, prompt/context files and lifecycle recreation. Use synthetic files and local canaries.
Exit: the baseline fails the isolation assertions for the expected reasons; every discovery path has a named owner/test or a documented blocker. No claim based only on an unrecognized new flag.
S3-G2 · Pi dependency patch

Enforce the policy throughout startup and reload.

  • Add early policy parsing, immutable policy plumbing and explicit settings/auth/resource construction. Gate command dispatch and import-time side effects where the audit finds them.
  • Skip implicit migration and discovery at the source; do not merely catch errors after a read or mutation. Ensure both initial and trust/reload resource paths bypass package resolution.
  • Add focused regression tests for managed behavior and compatibility tests for ordinary CLI behavior. Exercise conflicting flags and unsupported lifecycle commands.
  • Run the fork's required checks and hermetic tests. Record its patch provenance, lockfile/toolchain identity and minimal diff from the consumer baseline.
Exit: managed tests pass, deliberate regressions make them fail, and normal CLI behavior remains covered. Produce an unpublished candidate from an exact commit.
S3-G3 · FingerTrap integration

Select the candidate through the shared launch resolver.

  • Implement descriptor v2 and exact candidate identity selection in the internal fixture path. Keep production composition disabled.
  • Add the policy argument through the shared resolver so RPC and PTY cannot diverge. Reject missing/unknown capability, wrong hashes, old descriptors and caller-supplied overrides before spawn.
  • Permit project .pi only for the policy-capable fixture. Retain other S3 guards and the separate application/profile/artifact roots.
  • Exercise cross-profile concurrency and confirm unchanged user-managed executable resolution and shell-pane inheritance.
Exit: host tests prove both transports select the same policy; tampering or unsupported artifacts cannot start a managed child.
S3-G4 · Actual artifact qualification

Prove behavior through the real process paths.

  • Build a complete candidate inventory with source, dependency and executable digests. Run the acceptance matrix below against the actual binary, directly and through the published sidecar/native PTY companion.
  • Use a clean local Tart VM for macOS qualification. Exercise startup, reload, supported session recreation, cancellation, shutdown and failed startup without real provider credentials.
  • Replay RPC goldens and re-record changed-contract scenarios keylessly twice, comparing normalized results. Audit protocol/extension drift instead of accepting it automatically.
  • Run affected repository checks and the required platform matrix. Record unsupported or untested platforms explicitly; a macOS pass does not qualify Linux/Windows managed binaries.
Exit: retained evidence identifies the exact candidate, observable filesystem/process outcomes, mutation results, transport coverage and remaining platform limits.
S3-G5 · Qualification decision and handoff

Review the precise pin before promotion.

  • Publish a durable qualification report and companion PR references, with exact source/artifact identity, fork patch accounting, compatibility results and rollback instructions.
  • Present the reviewed candidate for the separate baseline/pin decision. Apply the approved pin and corresponding contract/provenance changes only after that decision, then verify the promoted identity.
  • Mark S3 discovery qualification complete only when the selected artifact satisfies the acceptance criteria. Keep open items attached to #201/#202; neither issue closes solely because this blocker is removed.
  • Resume S4 profile-aware stores/resume/meters, then the remaining imports and S6 integration qualification.
Exit: a specific qualified artifact is selected and durably recorded. Until pin approval, status is “candidate qualified; promotion pending,” not “S3 complete.”

07 · Acceptance

Verify observable behavior, including the paths after launch.

Required evidence before declaring discovery resolved
CaseRequired observation
Legacy migrationsProject .pi/commands remains in place; no prompts directory appears. Synthetic profile auth/session/keybinding/helper migration inputs are unchanged in direct Pi policy tests.
Implicit reads and commandsMalformed settings/models/auth and harmless command canaries in project, ancestor and synthetic home locations are not consumed. Instrumented service tests prove no implicit read path; external canary files/process observations prove commands did not execute. Unchanged file hashes alone do not prove files were never read.
Resource discoveryAmbient extensions, skills, prompts, themes and instruction/system files have no observable effect. A harmless selected extension loads once per runtime generation, with no duplicate registration; its explicit prompt and real cwd are verified.
Packages and helpersPackage resolution is not invoked in managed service tests. Synthetic package/helper inputs trigger no install, download or spawned helper; controlled network endpoints and process/file canaries record attempted activity.

Unsupported resume/switch/cwd transitions return a bounded error and leave policy/state intact. These rejections are temporary S3 limits, not completed S4 behavior.

Two profiles / both transportsActual PTY and RPC children retain the intended cwd and distinct environment/state roots during concurrent launches, failure and shutdown. No synthetic operator-home secrets appear in children; no parent environment mutation occurs.
Compatibility / regression proofOrdinary CLI and user-managed app behavior remain covered. Restore migration/discovery calls and remove capability enforcement one at a time: the relevant retained test must fail, then pass after restoration.
Artifact / protocolPublished-sidecar and clean-VM runs use the recorded candidate and native companion hashes. RPC replay and normalized recording evidence account for drift. Test reports state exactly which OS/architecture combinations ran.

All S3 qualification uses disposable synthetic data and keyless/local provider responses. No operator home or real repository configuration is supplied to destructive negative tests. The retained baseline reproducer and the new candidate qualifier must have clearly different success semantics.

If any reachable discovery path remains uncontrolled, retain the blocker and record it. A successful hello, a clean exit, a matching version string or a green launch-plumbing suite does not substitute for this matrix.

08 · Dependency decision

Build a candidate first; promote an exact artifact later.

Comparison base: start the focused patch from e7d09c9 in an isolated worktree. This keeps the first experiment attributable to the discovery fix. Review the proper maintenance-branch and forward-port arrangement in the Pi repository; do not reset its current branch or merge an old snapshot over newer fork work.

If implementing or building the fix requires a newer base or dependency changes, record the expanded diff and obtain a revised pin/base decision before treating that candidate as equivalent. 09 · Execution discipline

Use local macOS capacity and preserve resumable checkpoints.

Run focused fork checks locally first. FingerTrap's macOS CI and Apple Silicon packaging use the approved Tart runner; Windows/Linux retain hosted lanes. The current runner policy is restricted to FingerTrap and does not automatically authorize Pi-repository jobs.

Before an implementation source push, check the controller and explicitly enroll the new trusted PR according to the runner runbook. Establish its PR number using a documentation-only, CI-skipped draft checkpoint. Drain four local jobs for CI, or five with packaging. Preserve the immutable worker pin and later main-promotion mapping tracked in #208.

  • For each S3-G checkpoint, update STATUS before changes and append outcomes to WORK_LOG. Record exact next action, blockers, commands and candidate identities.
  • Distinguish proposed, implemented, locally verified, committed, pushed, CI verified, qualified and activated. A newer documentation commit does not inherit source verification without attribution.
  • Keep fixtures and essential reports in the repository. Record raw evidence paths and checksums; temporary files alone are insufficient for a cross-session handoff.
  • Checkpoint scoped changes in both repositories and link their issues/PRs. Carry this handoff branch's documents into the next FingerTrap implementation PR targeting dev.

For this proposal alone, validate the document and checkpoint it with CI skipped. Runtime builds are unnecessary for an HTML/status-only change.
