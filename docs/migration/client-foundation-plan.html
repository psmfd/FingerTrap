Item 1 implementation plan for discussion

PROPOSED · EXECUTION AWAITS MAINTAINER DISCUSSION

CF-1A · Freeze inputs and the worksheet

Verify the app archive/DMG, build commit, source/merge parents, checksums and ARM64 binaries. Resolve the supported production-baseline Pi executable and record its source/tag/digest. Record host/Tart and guest/base identities, installed tooling and intended provider/model. Prepare the mandatory worksheet before launching anything.

CF-1B · Prepare one owned clean guest

Use an inventoried clean macOS 15 base and a unique disposable VM name. Do not reuse an operator VM or the developer-toolchain CI base as evidence of a clean consumer environment. Record any preinstalled tools; do not claim a toolchain-free test if the guest contains them. CI drains and standalone acceptance must not overlap. Share only verified QA inputs read-only, then copy the candidate into the guest.

Run clean Finder installation/launch before adding optional testing tools. Record unsigned/Gatekeeper behavior without globally disabling Gatekeeper. No host operator settings, sessions, credentials, global npm tree or shell initialization are modified.

CF-1C · Exercise the actual client

Run shell transport/resize/split/close and missing/invalid explicit Pi requests. After clean launch is observed, install only the named QA baseline runtime and optional test tools in the guest. Exercise real Pi PTY and native RPC prompt/stream/abort/dialog/resume. Reuse owned synthetic fixtures where appropriate, but distinguish them from real supported-provider login and authenticated turn acceptance.

Observe the actual window/Tauri bridge. A sidecar-only script or an RPC response is not GUI acceptance. Real provider credentials must be supplied through the supported path in the disposable guest; none are copied from the host or placed in reports/screenshots.

CF-1D · Exercise persistence, lifetime and failure

Use guest-created test state for keychain save/relaunch/clear, repeated launch while normal/minimized/hidden, rapid startup launch and launch during quit. Record process identities before testing normal quit, a deliberately stopped owned sidecar and its twenty-second watchdog, controlled crash/recovery and prior-app upgrade. Observe descendants and cleanup; do not infer it from a self-reported success.

CF-1E · Triage and bounded corrections

Keep the first failure and exact artifact/process identities. Relate it to #102/#106/#107/#112/#175/#186/#187 where applicable, or file a concrete defect. Name and scope the affected files before corrective implementation. Preserve a failing regression where appropriate, make the bounded fix, then rerun affected acceptance on the replacement artifact. Passing an unrelated case does not repair a failed row.

CF-1F · Review and cleanup

Record pass/fail/blocked/not-run for every required case, redacted supporting observations, artifact transitions and open defects. Independently verify owned process/VM cleanup and preserved operator state. Review baseline captured versus baseline accepted with the maintainer, then record the exact next action for CF-2.

Capture exit: every mandatory case has an observed result or an explicit blocker, exact inputs and supporting evidence. Acceptance exit: mandatory checks pass on the selected bytes, blocking defects have fix/retest evidence, cleanup verifies and the maintainer records acceptance. A blocked or skipped real-Pi/provider row is not accepted.

Acceptance and evidence contract

The CF-1 worksheet defines twelve mandatory cases and required identity/evidence fields. No case has been run for CF-1 yet. Keep source/CLI qualification, package verification, GUI/provider acceptance, CI and production activation as distinct facts.

Evidence to preserve for every run
  • UTC run ID; exact app source/build/package digests; Pi tag/source/executable digest; previous-app identity for upgrade checks.
  • Base-image identity, guest macOS/build, architecture, preinstalled tool inventory and Tart version.
  • Per-case expected behavior, status, actual observation, sanitized evidence references and defect links.
  • Fixture versus real provider distinction; provider/model/login path without credentials, tokens, request content or sensitive logs.
  • Before/after process ownership, guest/host observations, cleanup confirmation and remaining blockers.

Candidate binaries and private raw evidence belong under an ignored .artifacts/client-baseline/<run-id>/ directory. Durable sanitized summaries and essential fixtures belong in the repository. Rebuilds receive new byte identities; earlier acceptance does not transfer automatically.
